# الويب والأندرويد على قاعدة Firebase واحدة

المشروع الحالي: `halaqat-app-272ff`. لم تُنشأ قاعدة أخرى ولم تُنقل البيانات الحالية.

## ما تغير

- واجهة ويب مبنية من شاشات Flutter نفسها الموجودة في الأندرويد.
- تهيئة Firebase للويب من إعدادات التطبيق المسجل في Firebase Hosting، مع التحقق من تطابق projectId مع الأندرويد.
- مستمعو Firestore يحدثون الحضور والإنجاز ولوحة الشرف وملخصات المدرسة ولوحة المالك؛ مسودات الحضور المحلية تبقى حتى حفظها.
- معاملات رصد بمعرف ثابت لكل طالب/يوم تحفظ سجلات المعلمين الآخرين وتمنع تكرار السجل بين الجهازين؛ القيم القديمة تستبدل فقط للطلاب المرسلين.
- فلترة صلاحيات المعلم في الخادم وقواعد Firestore، ومنع المعلم من تعديل إدارة المدرسة أو حسابات المعلمين.
- مشاركة Excel تعمل دون ملفات محلية خاصة بالأندرويد، وبناء CI للويب وAPK.

## التفعيل في المشروع القائم

1. تم التحقق من الوصول إلى المشروع الأصلي بحساب مالكه وتسجيل تطبيق الويب `halaqat_web` داخل المشروع نفسه. لا تنشئ Firestore أخرى.
2. نشر الويب معد على GitHub Pages مجانًا. خدمات Firebase الحالية على خطة Blaze بحسب الاستخدام؛ الاستضافة المجانية لا تجعل استهلاك قاعدة البيانات أو Functions مجانيًا بلا حدود.
3. راجع التغييرات والاختبارات، ثم انشر Functions والقواعد والفهارس مع النسختين. الإصدار القديم من APK قد يرسل كل الصفوف المعروضة؛ الإصدار الجديد يرسل الصفوف التي عدّلها المستخدم فقط، لذا حدّث المستخدمين إلى APK الجديد.
4. ابنِ الويب من `flutter_app` بالأمر `flutter build web --release`، ثم انشر من جذر المشروع: `firebase deploy --only hosting,functions,firestore --project halaqat-app-272ff`.
5. الإعداد التلقائي يستخدم `/__/firebase/init.json` على Firebase Hosting. للاستضافة الأخرى يلزم البناء مع `--dart-define=FIREBASE_WEB_APP_ID=...` و`--dart-define=FIREBASE_WEB_API_KEY=...` من إعدادات تطبيق Web المسجل.
6. اختبر بحسابين منفصلين: المالك ينشئ مدرسة، المدير يضيف معلمين وطلابًا، والمعلم يرصد طالبًا من الأندرويد. تحقق من ظهور التغيير في الويب، ثم عدّل طالبًا آخر من الويب وتحقق من ظهوره في الأندرويد دون فقد الرصد الأول. تحقق كذلك من منع حساب مدرسة من قراءة أخرى.

لا تعرض صفحة أو APK جديدين على المستخدمين قبل نشر الخادم والقواعد المتوافقة وإتمام هذا الاختبار. صلاحيات Google، وتسجيل Web app، واختبار البيانات الحقيقية تعتمد على الوصول إلى المشروع الحالي.

## النشر الآلي

الملف `.github/workflows/pages.yml` يبني الويب بإعدادات تطبيق Web المسجل، ويشترط نجاح نشر Functions وقواعد Firestore قبل نشر واجهة الويب. إعدادات Firebase الخاصة بالعميل عامة، وليست صلاحية لإدارة المشروع.

يحتاج النشر إلى اعتماد موجود ضمن GitHub Actions Secrets باسم `FIREBASE_TOKEN` أو `FIREBASE_SERVICE_ACCOUNT_HALAQAT_APP_272FF` (ويقبل أيضًا `FIREBASE_SERVICE_ACCOUNT`). لا تضع أسرار الإدارة في المصدر أو المحادثة. إذا لم يوجد اعتماد، تتوقف المهمة قبل نشر العميل حتى لا يستخدم بروتوكول الرصد الجديد مع خادم قديم.

يلزم أن يكون مصدر GitHub Pages هو GitHub Actions. تحديث الفرع main يشغّل البناء والنشر، ويمكن إعادة التشغيل يدويًا من Actions بعد إعداد الاعتماد. لا يُعد نجاح البناء وحده دليلًا على نجاح النشر أو المزامنة الحية.
